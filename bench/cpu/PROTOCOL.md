# CPU tier: measurement protocol

Fixed before the first timed run of the CPU-tier work (Phase 0 baseline, offline
stakes, and the Phase 1 campaign). The configs are generated by
`bench/cpu/matrix.py`; each runs through `bench/runner.py --mode cpu-baseline`,
`bench/child_run.py` and `bench/cpu/child.py`.

Goal under test: the CPU route of `apriori()` (no `use_gpu`, no `streaming`;
`sparse=False` and the default `sparse=None`) faster than efficient-apriori on
every regime below, single-threaded and multi-threaded, with identical output.

## Box

Cloud container: 4 vCPU Intel Xeon @ 2.10 GHz (Sapphire Rapids, KVM, one thread
per core, 260 MB L3), 15 GB RAM, no GPU. Python 3.13.16, Polars 2.0.0, NumPy
2.5.2, SciPy 1.18.0, efficient-apriori 2.0.6, `et_miner_rust` 0.3.0 built with
`maturin develop --release`. The runner records the full environment in
`env.txt`. "Physical core count" means the container's 4 vCPUs; the host
topology behind them is unknown.

## Arms

| arm | call (timed) |
|---|---|
| `F-polars` | `apriori(df, use_gpu=False, sparse=False, n_jobs=n, profile=True)` |
| `F-auto` | the same with `sparse=None` (the default) |
| `F-sparse` | the same with `sparse=True`; the Rust extension is installed |
| `EA` | `efficient_apriori.itemsets.itemsets_from_transactions(tuples, (min_count − 0.5) / N, max_length=ml)` |

- EA follows the CLAUDE.md oracle convention: `min_count = _min_count(min_support, N)`
  and an explicit `max_length`, which is the config's or, when it has none, the
  longest transaction (the exact bound; efficient-apriori defaults to 8).
- EA's timed call is `itemsets_from_transactions`, not `efficient_apriori.apriori`:
  the latter also generates rules inside the same call, and ET-Miner's
  `apriori()` returns itemsets only. The rule step's cost is measured once,
  offline, and reported next to EA's row.
- The goal arms are `F-polars` and `F-auto`. `F-sparse` is a reference arm.

## Thread settings

| setting | env | `n_jobs` |
|---|---|---|
| `T1` | `POLARS_MAX_THREADS`, `RAYON_NUM_THREADS`, `MKL_NUM_THREADS`, `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS` = 1 | 1 |
| `T4` | the same five = 4 | 4 |

EA is single-threaded either way and runs once per rep under the `T1` env; its
row is the reference for both settings. Every row records the process CPU
seconds of the timed call (`cpu_s`), so a `T1` row that used more than one core
shows as `cpu_s / wall_s > 1`.

## Timing

- Fresh process per config. The dataset is loaded into memory before the timer
  starts: a Polars DataFrame with an `items` list column for F; for EA the list
  of tuples, whose conversion (`to_list()`, then `tuple` per row) is timed
  separately as `convert_s` and is not part of EA's time.
- Warm-up before the timed call: the same arm on a 20,000-row slice of smoke
  (min_support 0.02, max_length 3).
- The timer covers the mining call only. EA's result frame is built after it.

## Metrics per row

- `wall_s`; per level `n_candidates`, `n_frequent`, ms.
- Per-level phase split (`bench/cpu/split.py`): matrix build, candidate
  generation, counting (length filter, density estimate, CSR conversion, K=2
  sparse product and look-ups, the Rust call, Polars expression counting and its
  collect), and the rest of the level (inference, merge, threshold filter,
  emit). The `profile=True` ProfilingSession phases are stored alongside. EA:
  index build, then per level candidate generation and counting.
- `cpu_s`; `peak_rss_mb` (sampled every 0.1 s during the call), `rss_start_mb`,
  and `ru_maxrss_mb` (the process high-water mark, including load and warm-up;
  this is the number the 25 % memory rule uses).
- Result signature (`n_itemsets`, `sum_counts`, `itemset_hash`), the prefix-group
  shape per level (`group_stats`), logged fallbacks, host and versions.
- A config killed at its cap keeps the levels it finished (`partial`).

## Repetitions and order

- 3 reps, rep-major. Within a rep the workloads run in the table's order. The
  seven configs of a workload run as `F-polars-T1, F-polars-T4, F-auto-T1,
  F-auto-T4, F-sparse-T1, F-sparse-T4, EA` on even reps and in reverse on odd
  reps.
- Budget: 6,300 process-seconds (1.75 h) for the campaign; the runner runs with
  `--max-hours 1.9` as a hard stop. Caps: 600 s per F config, 900 s per EA
  config. A cap hit is a lower bound, keeps its finished levels, and is never
  repeated.
- Reps 1–2 are budget-gated (`bench/cpu/matrix.py::rep_budget_skip`): once every
  rep-0 row exists, the base configs are sorted by rep-0 process seconds and
  reps 1–2 run for the longest prefix whose doubled cost fits 6,300 s minus the
  rep-0 total. Configs outside it have one rep, reported as a single value
  marked "1 rep".
- Cells are medians with [min, max] over the reps that ran.
- The offline stakes (L1–L5) run after the campaign, with nothing else on the
  box, within 15 minutes in total.

## Correctness

- Every ok row of a workload, EA included, has one signature; the runner's
  `check_equivalence` fails the campaign on a divergence.
- Planted motifs (smoke, deepk, skew): mined count ≥ planted count.
- A logged fallback marks the row (rule 1 below).
- The tier-equivalence chain (`tests/test_tier_equivalence.py`) and the SON and
  free-set tests pass on the measured tree before the campaign starts.

## Phase 0 decision rules (stakes)

- **Exactness.** A stake must reproduce its level's frequent set and absolute
  counts exactly (asserted against the same tree's output); otherwise no-go.
- **Cost model.** Projected time of a regime = the baseline row (same arm, same
  thread setting) with the replaced phases swapped for the stake's measured
  time at that thread setting.
- **Go** when the projection meets rule 2 against the current baseline in at
  least one regime, and the new structure's projected peak RSS stays within 25 %
  of that row's `ru_maxrss_mb`, or the lever states a memory budget with a
  fallback (tested in Phase 1) that does. **No-go** otherwise.
- **Build order.** Dependencies first (a lever whose representation another lever
  uses comes before it), then by projected saving summed over regimes.

## Phase 1 decision rules (from `bench/consolidation/PROTOCOL.md`)

1. **Signature mismatch or logged fallback** disqualifies the variant.
2. **Win.** Median ≥ 10 % below the alternative, the [min, max] ranges do not
   overlap, and it saves ≥ 1 s absolute.
4. **Partial winner.** A variant that wins some regimes and loses others stays
   only with a dispatch rule from facts known before the level runs (candidate
   count, previous-level size, prefix-group histogram, item count, rows after
   the length filter, mean support of the previous level); record the measured
   crossover. Without such a rule, keep the variant with the best geometric-mean
   time and record what it loses and where.
5. **Ties.** On a tie everywhere, keep what serves the most routes with the least
   code; then the lower peak RSS.

- **Goal test.** `F-polars` and `F-auto` each win against EA under rule 2 in
  every regime. Interpretation fixed here: where EA's median is below 10 s, the
  ≥ 1 s floor is replaced by 10 % of EA's median, because the floor is out of
  reach there by construction.
- **Memory.** `ru_maxrss_mb` must not grow more than 25 % in any regime without
  the owner's approval.
- The Phase 1 campaign repeats this matrix and procedure on the Phase 1 tree. Its
  repetition budget is agreed with the owner before it runs.

## Interpretations fixed here

- A regime is one workload at one thread setting.
- A config that errors or hits its cap cannot win; a cap hit's time is a lower
  bound.
- The harness was functionally checked on smoke (three configs) and once on
  or005 (`F-sparse-T4`, while a test run shared the box) before this protocol
  was committed. Those rows are discarded.

## Amendment 1 (2026-10-07, approved by the owner after rep 0 of or002)

Rep 0 ran over the budget. or002's F configs took 559–595 s each (one hit
the 600 s cap), so rep 0 alone exceeded 6,300 s; the budget rule then admits no
rep 1–2 at all, and the first invocation's 1.9 h stop fell inside or0001k2
(`F-sparse-T1`, `F-sparse-T4` and `EA` of rep 0 did not run). The owner
approved about an hour more:

- A second invocation (`--max-hours 1.1`) finishes rep 0 and runs reps 1–2 for
  every config of smoke, deepk, skew and or005 (`EXTRA_REP_WORKLOADS` in
  `bench/cpu/matrix.py`). wide, or003, or002 and or0001k2 keep one rep; their
  cells are marked "1 rep".
- The second invocation runs at a later commit. Between `b40a1dd` and it only
  `bench/`, documentation and licence files change; `src/` and `rust_ext/src/`
  are identical (checked with `git diff` before it starts), and the Rust
  extension is not rebuilt.
