# Consolidation measurement protocol

Fixed before the Phase 2 campaign ran. The configs are generated by
`bench/consolidation_matrix.py`; each is run by `bench/consolidation_run.py`
through `bench/runner.py --mode consolidation`.

## Box and budget

2× RTX 3060 12 GB (sm_86, no P2P), Ryzen 5 5600X (6C/12T), 31 GB RAM. Budget:
≤ 8 GPU-hours, counted as Σ (process wall × devices the config uses; a CPU
config counts as one). The campaign runs with `--max-gpu-hours 7.5`, leaving
room for the calibration and microbench runs that preceded it.

Every config pins `POLARS_MAX_THREADS`, `RAYON_NUM_THREADS`, `MKL_NUM_THREADS`
and `OMP_NUM_THREADS` to 6 (the physical core count), passes `n_jobs=6` where it
applies, sets `ET_MINER_KERNEL_VARIANT` and `ET_MINER_TILED_MIN_GROUP_PAIRS`
explicitly on the routes that read them, restricts one-GPU routes to device 0
(`CUDA_VISIBLE_DEVICES=0`), and sets `ET_MINER_DISABLE_NCCL=1` for the row-split
miner on one device. `MKL_NUM_THREADS` is not a hard cap: inside its parallel
sections `core/sparse.py` sets `cpu_count // n_workers` MKL threads per worker.

## Workloads (regimes)

| id | dataset | min_support | max_length | what it stresses |
|---|---|---|---|---|
| smoke | smoke preset (60K rows) | 0.01 | — | small, deep; the tier-gate preset |
| deepk | deep_k (1M) | 0.02 | — | planted 10-item motifs, K≤11 |
| skew | skewed_rows (1M) | 0.02 | — | nnz clustered in the first 20% of rows |
| oom2 | oom_regression (500K, 30K items) | 0.00003 | 2 | 450M K=2 candidates |
| sk2ml2 | stress_k2 (2M, 35K items) | 0.000015 | 2 | 612M K=2 candidates, 8.75 GB bitvecs |
| sk2ml3 | stress_k2 | 0.000015 | 3 | ~12B K=3 candidates (conditional, below) |
| dsl | deep_sparse_large (20M) | 0.015 | — | 577K itemsets to K=16 at scale; mean support below n/32 from K≈5 |
| wide | wide_vocab (100K, 2.3K frequent items) | 0.004 | — | CPU sparse auto-selection |
| or005 / or003 / or002 | Online Retail II (36K invoices) | 0.005 / 0.003 / 0.002 | — | real data, 10K / 62K / 436K itemsets |

SON regimes: `dsl` with `chunk_size=5,000,000` and `deepk` with
`chunk_size=250,000`, both asserted to run exactly 4 chunks.

## Configs per decision point

Config ids are `<workload>-<config>`; variants are pinned by env.

| DP | configs | metric |
|---|---|---|
| DP1 miner | `A1-{shared,legacy}`, `B1`, `C1-{shared,legacy,tiny0}` on every in-core workload | wall_s; a miner's time in a regime is its fastest variant's |
| DP2 K=2 kernel | the same runs, plus `C2-{shared,legacy}` | the K=2 level ms, within one miner |
| DP3 K≥3 kernel | the same runs (B contributes `count_k3plus_gpu_resident`) | Σ K≥3 level ms, within one miner |
| DP4 tiled fallback | `C1-shared` (tiny groups < 64 pairs, mega-groups and multi-chunk K=2 on the per-candidate kernel), `C1-tiny0` (tiny groups tiled too), `C1-legacy` (everything per-candidate) | wall_s |
| DP5 layout | `C1-{shared,legacy}` dense vs `-auto` vs `-k3`, and `A1-{shared,legacy}-auto`, on smoke/deepk/skew/dsl/or003/or002 | wall_s |
| DP6 multi-GPU | `C2-{shared,legacy}` on smoke/deepk/skew/oom2/sk2ml2/dsl; `Asplit2-shared`, `Bsplit2` on oom2/sk2ml2 (the only regimes above the split thresholds) | Σ K≥2 level ms (the split routes receive prebuilt bitvecs; their build is timed separately) |
| DP7 SON | `D1-resident`, `D1-gpu`, `E2` on dsl and deepk; `D1-cpu` on deepk | wall_s and per-pass time, against the regime's in-core winner |
| DP8 CPU | `F-polars`, `F-sparse` (Rust), `F-sparse-norust`, `F-auto` on smoke/deepk/skew/wide/or005/or003 | wall_s |
| DP9 Rust host roles | `C1-{shared,legacy}-norust`, `C1-{shared,legacy}-noprune` on smoke/deepk/skew/dsl/or003/or002; `C1-legacy-free(-norust)` (free-sets, R4) on smoke/deepk/dsl/or002; per-call microbench (`bench/microbench_rust.py`) on dsl and stress_k2 | per role: per-call Rust vs fallback time (R2–R4); Σ K≥3 level ms of `F-sparse` vs `F-sparse-norust` (R1) |
| DP10 A/B arms | `C2-shared-filter-{cupy,cpu}` on sk2ml2, `C2-legacy-filter-{cupy,cpu}` on dsl, `C2-legacy-balance-nnz` on skew/dsl, each against the same-variant `C2` config | wall_s |

DP10 and DP9 configs use the kernel variant that was faster for that workload
in the calibration runs (shared on stress_k2, legacy on deep_sparse_large), so
the host-side difference is not diluted by a slow kernel; DP9 runs both
variants on the smaller workloads.

`sk2ml3` runs a config only if its `sk2ml2` twin's K=2 median is within 2× of
the fastest K=2 median among `sk2ml2` configs **using the same number of GPUs**,
judged on the reps recorded when the config comes up (rep 0 judges on one
rep). Candidates: `A1-shared`, `A1-legacy`, `B1`, `C1-shared`, `C2-shared`,
`C2-legacy`, `Asplit2-shared`, `Bsplit2`.

## Repetitions and order

Fresh process per config; the child compiles every registered kernel on every
device it uses and runs the same route on a 20,000-row slice of `smoke` before
the timed call. 3 reps, rep-major, one-off axes (DP5–DP10) first, the smoke and
deep_k reps 1–2 last so a `--max-hours` stop sheds those first. The SON configs
on dsl run once with a 600 s cap (their calibration estimate is hours); a cap
hit is recorded as a lower bound. Medians are reported with [min, max].

## Decision rule (as given; applied mechanically)

1. **Signature mismatch or logged fallback.** Either disqualifies that variant.
   Report it as `(must-fix)` and remove nothing on that DP until it's fixed.
2. **Winning a regime.** A variant wins a regime when all three hold: its
   median is ≥ 10% below the best alternative; the two [min, max] ranges don't
   overlap; it saves ≥ 1 s absolute.
3. **Removal.** Remove a variant that wins no regime, provided every capability
   it offers is kept elsewhere or ported in Phase 3, with tests.
4. **Keeping a partial winner.** A variant that wins some regime stays only if
   a dispatch rule can select it from facts known before the level runs
   (group-size histogram, candidate count, mean support, free VRAM). If such a
   rule exists, implement it and record the measured crossover; if not, keep
   the variant with the best geometric-mean time across regimes and record what
   it loses and where.
5. **Ties.** On a tie everywhere, keep whatever serves the most routes with the
   least code; break remaining ties on peak VRAM.
6. **SON.** This rule never removes SON (DP7).
7. **Rust, per role (R1–R4).** A role goes when its fallback is within 10% in
   every regime where the role runs, or the role itself disappears.

Interpretations fixed here:

- A regime is one workload row above (a free-set run is its own regime).
- A config whose run errors (including out-of-memory) or times out cannot win
  that regime; it is not a signature mismatch. A timeout's time is a lower
  bound.
- "Best alternative" in rule 2 is the fastest other variant of the same DP in
  that regime; rule 2 is evaluated once per regime.
- DP1 compares miners by their fastest variant per regime, because DP2–DP4
  choose the kernels inside the surviving miner.
- Rule 4's facts are recorded per level by the child (`group_stats`: groups,
  candidates, median/max suffixes per group, share of candidates in groups of
  ≥ 64 pairs) from the level each K is generated from.
- For rule 7 the per-call microbench decides R2–R4 (fallback median within
  1.10× of Rust's on every dumped call); the end-to-end `-norust` runs must
  match signatures and are reported alongside.
